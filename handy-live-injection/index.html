What this is

This is RascalTwo's fork of Handy, a local speech-to-text app for macOS. It branches from v0.9.6, and the whole delta is a short stack of commits on that tag — git log v0.9.6..HEAD is always exactly what is mine. The headline commit adds one shortcut.

option+space
Transcribe

Stock. The whole transcription is pasted when you release the key.

ctrl+option+space
Transcribe Live

New. Types each word into the focused app as the model commits it.

option+shift+space
…with Post-Processing

Stock, and never live. An LLM rewrites the whole transcript; words already typed can't be un-typed.

There is no mode setting. The shortcut you press is the mode, exactly as post-processing has no "post-process my main key" toggle. That's not a stylistic choice — it's what makes the one genuinely broken combination unreachable instead of merely warned about. Post-processing rewrites the transcript wholesale, which cannot be reconciled with text already sitting in your document; because the binding decides, the post-processing shortcut simply has no way to be live.

Why the patch is small

Upstream already did the hard part. v0.9.0 integrated transcribe.cpp and does real streaming inference — several updates a second, each carrying a two-part split:

// what the stream hands back on every feed()
StreamText {
  committed:  "set the um retry"   // append-only. never revised.
  tentative:  " budg"              // still being reconsidered
}

Stock Handy renders both halves in the recording overlay and throws them away. This fork types the committed delta into your app and leaves tentative in the overlay where it already lives.

That split is the whole reason this is tractable. The thing that normally makes live dictation horrible — the model changing its mind and needing to backspace over what it already typed — does not arise, because committed only ever grows.

Complete words only, and why

Even with post-processing off and no custom words, Handy filters its output: remove_filler_words strips uh/uhm/hmm, and normalize_transcription_output collapses stutters and double spaces. Raw committed contains those words. The final text doesn't. So live-typed text is not naively a prefix of the final text — it has to be made into one.

Two rules do that. Only complete words are eligible — everything up to the last whitespace in committed — because the filler filter matches on \b word boundaries and can't safely run over a half-streamed word. Let "u" through and it gets typed a moment before the filter learns it was about to become "um" and vanish. And the whole eligible prefix is re-filtered and re-diffed on every update, never each delta in isolation, which is what makes the filter's retroactive edits land: a filler is only droppable once the word after it arrives.

// transcription.rs — the entire decision
let end = committed.rfind(char::is_whitespace)?;
let eligible = post_process_transcription_text(committed[..end].to_string(), …);

match eligible.strip_prefix(already_typed) {
    Some("")   => None,                                // grew, but not past a boundary
    Some(delta) => Some((delta.to_string(), eligible)),  // type this
    None       => /* diverged — stop */ None,
}
The cost is one word, permanently. The trailing word waits for a whitespace boundary, and on top of that the genuinely uncommitted tentative tail hasn't been decided at all. That's why the last word or two arrive on release rather than as you speak. It is not a bug to be fixed later — the model hasn't chosen those words yet.

"Append-only" is a guarantee, not an observation

The whole design rests on committed never contradicting itself, so it's worth saying where that comes from. transcribe.cpp's commit_stream_text can only append, refuses any candidate boundary at or behind the current one, and bails outright if the raw hypothesis stops matching what was already committed. It snaps commit boundaries to UTF-8 character boundaries only — never to word boundaries — which is precisely why the complete-words rule above has to exist.

Measured as well as argued: zero divergences across a real session — 78 revisions, 2835 frames, 1237 characters, including one 87-second utterance.

live_delta still keeps a standing check, because a different model or a transcribe.cpp bump could break the assumption silently. If a committed ever fails to extend the previous one it logs

live paste: committed prefix diverged (typed "…", now "…")

and types nothing further for the rest of the utterance rather than garbling your text. Already-typed characters can't be recalled, so refusing to continue is the only safe move.

Live paste freezes its language evidence, and has to

v0.9.6 split filler removal into two tiers. uh/uhm/hmm are universal; um/ah/eh/ha are gated on knowing the output language, because um is a real word in Portuguese and German. When nothing else establishes the language, Handy falls back to running whatlang over the transcript behind a confidence gate.

That fallback cannot run on the live path, and the reason is structural. Detection is a function of the whole string, so on a growing prefix it resolves later than it does on the final text — upstream's own test has "um ok" returning no language while a full sentence returns en. Live paste would type um while the prefix was too short to detect, then, one word later, re-derive a prefix with um removed, no longer match what it had already typed, and hit the divergence guard. The feature would go silent four words into every sentence on any setup that leaves the language unresolved.

So live_delta passes allow_text_language_detection = false and reuses whatever evidence the engine resolved before the stream started. The price is that a gated filler can survive in live-typed text where detection would later have caught it. An occasional surviving um is what the feature costs to work at all, and live_paste_keeps_typing_when_text_detection_would_flip_mid_utterance pins it — flip that false to true and the test fails, showing live paste stopping mid-sentence.

The final paste subtracts what was already typed

On release, nothing about the normal path changes: finalize() returns the whole utterance, post-processing runs on it, history records the full text. The only new step is that remaining_after_live strips the live-typed prefix off before the paste, so you get " attempts" and not the sentence a second time.

It has three outcomes, and the third is the interesting one. Nothing left → paste nothing. A remainder → paste that. And final text that doesn't extend the live-typed text → paste nothing and leave the live text standing, on the grounds that a duplicated utterance is worse than a slightly wrong one. That last branch shouldn't be reachable through the UI, since post-processing is a different shortcut; it exists because it's the failure that would hurt most.

A new binding has to be registered in three places

Adding a transcribe binding touches three files, and missing one fails quietly. This bug shipped here once.

WhereWhat it decides
ACTION_MAP
actions.rs		What the binding does — here, a TranscribeAction with live: true.
get_default_settings()
settings.rs		Its default shortcut. Must be distinct from the other two: a duplicate is rejected at registration ("already in use") and one of them silently dies.
is_transcribe_binding()
transcription_coordinator.rs		The easy one to miss. Skip it and the binding drops onto the plain press/release path: hold-to-talk regardless of your push-to-talk setting, and outside the coordinator's lifecycle serialisation.

All three now have tests pinning them — every_recording_binding_reaches_the_coordinator, live_paste_has_its_own_distinct_default_shortcut, and a pair of fork guards that fail loudly if a rebase reverts the bundle identity or turns the updater back on.

What it costs you

  • The last word or two always arrive on release. Structural, per above. Live paste feels like typing that trails you by about a word, not like a teleprompter.
  • Cancelling can't un-type what's already in your document. There is no undo channel; the words are in the app, and the app owns them now.
  • Clipboard paste methods are bypassed mid-stream. ctrl_v and friends would mean one clipboard write per committed word, which would destroy your clipboard. Streamed words are always typed directly; only the final word honours your Paste Method, along with the trailing space and auto-submit that are only correct once.
  • Paste Method "None" types nothing at all. The settings panel escalates that one to a warning; the rest are notices.
  • Non-streaming models produce no partial text, so the shortcut silently behaves exactly like plain Transcribe.
  • A gated filler can survive when the output language was never established — the frozen-evidence tradeoff above.
  • Anything that fights synthetic input fights this seven times instead of once. The mechanism is enigo's fast_text, the same call stock Handy makes, so an app that mangles a pasted transcription will mangle each word too.

One worry that turned out not to be real: push-to-talk is fine. enigo's macOS fast_text posts the literal Unicode string with CGEventFlagNull, explicitly ignoring held modifiers, so typing while the shortcut's own modifiers are physically down doesn't mangle the text. Tested.

The rest of the fork

Three things that aren't the feature but are the difference between a fork that works and a fork that eats itself.

  • The updater is off by construction. Upstream's minisign public key is bundled, so an update check would find upstream's latest release, verify the signature successfully, and replace the fork with stock Handy. Update checks default to false, and tauri.conf.json ships "endpoints": [] so the updater fails closed even if they're switched back on.
  • It signs with a real (self-signed, free) identity, not ad-hoc. macOS pins an Accessibility grant to the app's designated requirement, and ad-hoc signing pins it to the exact binary's cdhash — so every rebuild invalidates the grant, System Settings keeps showing the app ticked, and toggling the checkbox does nothing. A certificate pins to the identifier instead. Grant once.
  • Different bundle id (com.rascaltwo.handy), so it runs alongside stock Handy with separate settings, history and permissions, sharing the downloaded models. Both default the transcribe shortcut to option+space, and only one process can claim a global shortcut — so rebind one or quit the other.

Keeping current means rebasing onto upstream release tags, never main and never a merge, so git log v0.9.6..HEAD stays exactly the fork's delta. scripts/update-from-upstream.sh does the fetch, backup branch, rebase and verification — including the one check nothing else catches, that the bundle really was signed with the fork identity rather than falling back to ad-hoc.

Everything here is read out of the fork's own source — transcription.rs, actions.rs, clipboard.rs, transcription_coordinator.rs — and its tests.
